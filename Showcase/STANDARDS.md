# SHOWCASE STANDARDS

*The standard every sellable asset is produced to. Written 8 Aug 2026 by the Showcase seat, Phase 5 of BUILD_PLAN.md. No em dashes anywhere in this project, including inside CSS and JS comments.*

The founder's ruling this file exists to serve, from RUNBOOK.md:

> **SELLABLE = VISIBLE VALUE.** The customer never pays for what he cannot see. Every SKU page carries a REAL sanitized sample report (lab data, never employer data), professional screenshots (scripted headless-Chrome captures, consistent frame and branding), and a short video of the real run (terminal to report). Produced by the Showcase seat to standard, never ad hoc.

This page is written so that a different seat, months from now, can produce a matching asset for a new pack without asking anybody. If something here is ambiguous when you need it, that is a defect in this page: fix the page, then produce the asset.

---

## 0. THE ONE COMMAND

```
npm run build:showcase
```

That runs `scripts/showcase/build.mjs`, which produces every asset in `Showcase/samples/` and rewrites `Showcase/MANIFEST.json`. There are no manual steps, no hand cropping, no hand captioning, and nothing that has to be done in an image editor. An asset that cannot be regenerated by that one command does not belong in `Showcase/`.

Guarded by `test/showcase.test.js`, which runs inside `npm test`.

---

## 1. THE HONESTY RULE, WHICH OUTRANKS EVERYTHING ELSE HERE

**The OraDiscuss Health Check pack has never been run against a real Oracle database.** Every asset in `Showcase/samples/healthcheck/` is rendered from a synthetic lab collection written by hand at `scripts/showcase/lab/healthcheck/collection.txt`. The founder's field test is the designed gate for a real run, and it has not happened.

So this exact sentence, the PROVENANCE SENTENCE, travels with every asset:

> Sample rendered from a synthetic lab collection. Not output from a real Oracle database.

It appears, verbatim, in four places, and the build fails if it stops matching in any of them:

1. **In this file**, above.
2. **As a constant in `scripts/showcase/build.mjs`** (`PROVENANCE`), which is the only place it is authored.
3. **Burned into the pixels** of every framed image, in the caption strip, next to a `SYNTHETIC LAB DATA` pill. Burned in rather than only written in the manifest, because a caption that lives beside an image gets dropped the moment somebody pastes the image into a page, and pixels cannot be dropped.
4. **On every entry in `Showcase/MANIFEST.json`**, in the `provenance` field.

Rules that follow from it, and none of them are negotiable:

- **No asset, caption, filename, alt text or manifest field may state or imply that a real database was involved.** Not "from a live estate", not "from a production run", not "real customer data", not a hostname or SID that could be mistaken for one.
- **The video shows the command that actually ran, and only that.** `Showcase/samples/healthcheck/command.txt` is written by the render step and read by the frame generator, so a prettier command cannot be substituted. The console lines in the video are `run.log`, unedited.
- **When the field test happens, the assets are regenerated, not retouched.** See section 7.
- **A softened provenance line is a defect of the same class as a wrong number.** If a future seat believes the wording is too blunt for a sales page, that is a founder decision, not a seat decision.

## 2. WHAT DATA MAY APPEAR: SANITIZED LAB DATA ONLY

**Never employer data. Never a real customer hostname, SID, IP, path, schema name, or business name. Not even once, and not even blurred.** A blur is a reversible transform and a redaction bar is a promise about a file somebody else now holds. The only safe sample is one that never contained anything real.

The identifiers a showcase asset is allowed to carry are declared, not merely avoided. The guard asserts the allowed set positively, so a new identifier fails rather than passing because nobody thought to ban it.

| Kind | Allowed values | Why |
|---|---|---|
| Oracle SID and instance names | `ODCDEMO`, `ODCDEMO1`, `ODCDEMO2` | Invented. `ODC` for OraDiscuss, `DEMO` for what it is. |
| Host names | anything ending `.odclab.example` | `.example` is reserved by RFC 2606 and can never be registered. |
| IPv4 literals | `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` | The RFC 5737 documentation ranges. Routable nowhere. |
| Schema and object names | invented, generic (`APPOWNER`, `APPDATA`, `IX_ORDER_LINE_DT`) | Says nothing about any organisation. |
| File system paths | Oracle's own documented OFA layout under `/u01/app/oracle/...` | The default from the installer, which belongs to nobody. |

**The guard is a positive signature, deliberately.** `test/showcase.test.js` asserts that the SID present is one of the allowed three, that every IPv4 literal falls in a documentation range, and that every dotted lower case token in the lab inputs is on a declared allowlist. It does NOT contain a list of real names to search for. A denylist of real identifiers checked into a public repository is itself the leak it claims to prevent.

**The lab inputs are declared, including the ones that are stand-ins.** `Showcase/MANIFEST.json` carries a `synthetic_inputs` array naming every file the sample was built from and why. Today that is the collection, the pack config, and `scripts/showcase/lab/healthcheck/bin/lsnrctl`, a lab stub that stands in for the listener utility so the listener row reports a state instead of reporting that the capture machine has no Oracle install. The stub contacts nothing, lives only under `scripts/showcase/lab/`, and is never shipped inside `packs/`.

## 3. CAPTURE

The rig is `scripts/showcase/capture.mjs`. It drives headless Chrome over the DevTools Protocol. Every awkward looking thing in it is a platform bug that has already cost this project an hour, and each one is commented at the top of that file. The four that matter:

1. **Chrome 150 removed old headless**, so the `--screenshot` command line flag captures the VIEWPORT ONLY. There is no flag for a full page shot. Full page means: measure `scrollHeight`, resize the viewport to it, capture.
2. **`captureBeyondViewport` hangs above roughly 6000 device pixels.** The rig never passes it. Anything taller than the tile limit is captured as tiles and stitched.
3. **`Emulation.setDeviceMetricsOverride` rejects fractional heights**, and `scrollHeight` and `getBoundingClientRect()` are both fractional whenever a line box is. Every derived dimension is `Math.ceil`ed.
4. **Chrome 151 headless writes the `--screenshot` file and then lingers**, deadlocking `subprocess.run` past any timeout. The rig never uses `--screenshot`. It holds the browser open on purpose and kills it itself.

**The Chrome binary is searched for, never assumed.** `CHROME_PATH` overrides the search. A fresh `--user-data-dir` is created per run and deleted after, because a reused headless profile re-measures a cached page and a fix then looks unapplied.

### Fixed numbers

| Setting | Value | Notes |
|---|---|---|
| Device scale factor | **2** | Every shipped PNG is a 2x asset. Filenames carry `@2x`. |
| Screenshot viewport width | **1152 CSS px** | The artefact being photographed is rendered at this width. |
| Frame canvas width | **1280 CSS px** | So every shipped image is exactly **2560 device px wide**, always. |
| Frame padding | **64 CSS px** on all four sides | 1152 + 64 + 64 = 1280. |
| Tile limit | **2400 CSS px** viewport | 4800 device px, comfortably under the hazard at 6000. |
| Video and terminal stage | **1280 x 720 CSS px** | 2560 x 1440 captured, encoded at 1280 x 720. |
| Any resize | **LANCZOS**, via `scripts/showcase/stitch.py` | Nothing invents pixels. |

Height is whatever the content is. It is never padded to a round number and never cropped to one.

**Crops end at a boundary in the page, never at a magic pixel row.** The report hero (`healthcheck-report-summary@2x.png`) is cut 20px above the third `h2` in the document, measured live. A fixed pixel height goes stale the first time a section is added, and the crop then slices a table in half, which reads as a rendering fault rather than as a crop.

**A showcase asset never pans horizontally.** The rig throws if `scrollWidth` exceeds the capture width. The fix is the template, never a wider capture.

### Tiling, and the proof that it works

Tiling is exercised by lowering `tileMaxCss` and asserting the tiled capture is byte identical to the single shot capture of the same page. That was run in the session that built this rig, at `tileMaxCss` 400 against the full report page, and the two PNGs matched. Re-run it after any change to `captureOne` or `stitch.py`:

```
node scripts/showcase/verify-tiling.mjs
```

A guard nobody has watched fail is not a guard, and a tiling path nobody has watched run is not a path.

## 4. FRAME, BACKGROUND, BRANDING

The frame template is `scripts/showcase/templates/frame.html`. It is a real page, captured by the same rig, rather than a composite drawn in PIL. That is deliberate: typography, radii and shadows then come from CSS a future seat can read and edit, and there is no font file to hunt for.

- **Background**: brand Field `#FAFBFD` from `DESIGN.md`. Flat. No gradient, no aurora, no texture. The artefact is the subject; the frame is a mount.
- **The artefact panel**: 1px hairline `#DFE5EE`, 14px radius, `0 18px 44px rgba(11,27,52,.11)` shadow. The Health Check report is a dark surface on a light mount, and that contrast is the point: it reads as a product screenshot on a brand page rather than as a page that cannot decide on a theme.
- **Header strip**: an Oracle red `#C74634` dot, then the wordmark `OraDiscuss` at 19px/700, tracking -.018em. On the right, the artefact tag in mono, 11px, uppercase, .12em tracking, ink 3 `#626C80`. Format: `PACK NAME vX.Y.Z · FILENAME`.
- **Caption strip**: a `SYNTHETIC LAB DATA` pill outlined in Oracle red, then the provenance sentence in bold ink, then one or two sentences of plain description in ink 2 `#4D5A74`. Max 78ch.
- **No webfonts.** An asset that renders differently depending on whether a font server answered is not a reproducible asset. Sora, Archivo and JetBrains Mono are the site's brand faces; the showcase frame uses the system UI and system mono stacks so the same command produces the same pixels on any machine. If brand fonts are ever wanted here, they must be checked in as files first.
- **No inline `<script>` in any showcase template.** None is needed, and a dead inline script is invisible in markup: a single `//` comment inside a one-line emitted script has killed a whole page in this project before. Reveal sequences are produced by generating one file per state, not by animating in the page.
- **No Oracle logo, ever.** The ACE Associate badge is the only Oracle programme mark permitted anywhere in this project, under the personal use limits.

## 5. FILE NAMING AND DIRECTORY LAYOUT

```
Showcase/
  STANDARDS.md                  this file
  MANIFEST.json                 generated, never hand kept
  samples/
    <pack-id>/
      report.html               the pack's own output, unedited
      briefing.json             the pack's own output, unedited
      run.log                   the unedited console output of the run
      command.txt               the exact command that ran
      exit-code.txt             the exit status
      images/
        <pack-id>-<artefact>[-<variant>]@2x.png
      video/
        <pack-id>-<subject>.mp4
        <pack-id>-<subject>.gif
scripts/showcase/
  build.mjs                     the one entry point
  capture.mjs                   the Chrome/CDP rig
  stitch.py                     PIL: stitch tiles, pan frames, LANCZOS resize
  render-sample.sh              drives the REAL pack through --render-only
  verify-tiling.mjs             proves the tiling path against the single shot path
  selftest-guards.sh            breaks one thing per case and watches each guard fire
  templates/                    frame.html, code.html, terminal.html
  lab/<pack-id>/                the synthetic inputs, declared in the manifest
```

**Naming**: lower case, hyphen separated, no spaces, no dates, no version numbers in the filename. `<pack-id>-<artefact>[-<variant>]@2x.png`. Every raster asset carries `@2x` because every raster asset is captured at device scale factor 2. A file whose name has to change when it is regenerated cannot be linked from a page, which is why the pack's timestamped output filenames are normalised to `report.html` and `briefing.json` on the way in.

**The pack's own outputs ship unedited.** `report.html` and `briefing.json` are byte for byte what `health_check.sh` wrote. They are assets in their own right, not just sources for screenshots: the RUNBOOK requires a real sample report on the SKU page, and a screenshot of a report is not a report.

## 6. THE MANIFEST, AND WHY IT IS GENERATED

`Showcase/MANIFEST.json` is written by `build.mjs`. It is never hand edited.

The build **declares** the assets it produced, then **walks** `Showcase/samples/` and **refuses to write a manifest that disagrees with the directory**. `test/showcase.test.js` then checks the same correspondence again, independently, in both directions.

That double check is not paranoia, it is scar tissue. This repository has twice shipped a fan-out step that named its inputs, and both times the input added afterwards was dropped in silence while every test stayed green. A registry that is trusted rather than checked is a list that lies with authority.

Every entry carries: `path`, `kind`, `pack`, `bytes`, `produced_by`, `provenance`, `caption`, and for images `width`, `height`, `dsf`, `caption_burned_in`.

**`caption` is binding on whoever publishes the asset.** No showcase asset goes on a page without its manifest caption rendered next to it. For images the provenance is also in the pixels as a backstop; for `report.html`, `briefing.json` and the video files there is no backstop, so the page must carry it.

## 7. WHEN THE FIELD TEST HAPPENS

The pack gets run against a real database at the founder's field test. That is a standing gate: field-test sign-off is what promotes any pack v0.9 to sellable v1.0.

When it happens, the showcase is rebuilt from the real collection with **no code change**:

```
ODC_SHOWCASE_COLLECTION=/path/to/health_raw_SID_ts.txt npm run build:showcase
```

Then, and only then, three things are corrected **by hand, deliberately**:

1. The `PROVENANCE` constant in `scripts/showcase/build.mjs`.
2. Section 1 of this file.
3. The allowed identifier table in section 2, because a real collection carries real identifiers and **must be sanitized before it is used as a showcase source**. Sanitizing means rewriting the SID, host names, schema names and paths to the invented ones above, in the raw collection file, before it is rendered. A real report is not publishable simply because it is real.

The data path is a flag. The honesty strings are hand edits on purpose: they are meant to resist being swapped by accident, because the day the data changes is exactly the day nobody is thinking about the caption.

## 8. THE VIDEO

- **Content**: terminal to report. The real command, revealed as if typed, then the real console output line by line, then a cut to the framed report and a slow eased pan down it, ending on the caption strip so the provenance sentence is the last thing on screen.
- **Format**: H.264 in MP4, `yuv420p`, 30fps, CRF 20, `+faststart`. **1280 x 720.** Both dimensions even, because H.264 refuses odd ones.
- **A GIF ships beside it**, 800 x 450 at 10fps with a diff palette, for surfaces that will not play video.
- **Timing** comes from an ffmpeg concat list with a per frame `duration`, so a held frame costs one file rather than thirty. Typing steps hold 0.09s, output lines 0.5s, the last line 1.6s, pan frames 0.042s, and the final frame 2.0s.
- **Motion is cuts and one eased pan.** No zoom, no Ken Burns push on any artefact.
- **`ffmpeg` is checked for at build time.** If it is absent the frames and the concat list are still produced, the manifest records `video_encoded: false` with the reason, and the build says so loudly. It never emits a manifest entry for a video that was not encoded.
- **A video is not done until somebody has opened it.** `ffprobe` its duration and dimensions, extract frames across the whole timeline, and look at them. A file of the right size that plays nothing looks identical to a good one from the shell.

## 9. THE CHECKLIST FOR A NEW PACK

1. Write `scripts/showcase/lab/<pack-id>/collection.txt` and `config.env` using only the identifiers in section 2. Put them under `scripts/showcase/lab/`, **never under `packs/`**: `scripts/publish-pack-to-project.sh` exports `packs/` to the customer facing mirror, so a fixture parked there ships.
2. Extend `render-sample.sh` to drive that pack's real script through its real `--render-only` path. Never re-implement a renderer for a sample.
3. Add the pack's jobs to `build.mjs`. Reuse `frame.html`; add a template only if the artefact is genuinely a new kind.
4. Run `npm run build:showcase`, then **look at every asset as pixels**, then `npm run build && npm test`.
5. Watch the guards fail on purpose before trusting them. Section 10.

## 10. THE GUARDS, AND WATCHING THEM FAIL

`test/showcase.test.js` fails when this standard is violated. It covers:

- every file in `Showcase/samples/` is registered in the manifest, and every manifest entry exists on disk, checked in both directions against the directory rather than against a hand kept list;
- no em dash in `STANDARDS.md`, in the manifest, in any text asset, in any caption, or in any showcase script or template;
- the provenance sentence is present verbatim in this file and on every manifest entry, and the frame template that burns it into the pixels still contains it;
- image dimensions on disk match the manifest, are exactly 2560 device px wide, and are even in both axes;
- the capture constants in the manifest match the numbers in section 3 of this file;
- sanitization: only the allowed SIDs appear, every IPv4 literal is in a documentation range, and every dotted token in the lab inputs is on the declared allowlist.

**Every one of these must be watched failing against deliberately broken input before it is trusted.** That is not a manual ritual anybody has to remember. The test reads its roots from `SHOWCASE_DIR` and `SHOWCASE_SCRIPTS`, and there is a harness that copies both, breaks exactly one thing per case, and fails unless the guard built to catch it actually fires:

```
npm run test:showcase-guards
```

It also asserts that an untouched copy passes, because a suite that fails on everything catches nothing. Every case is one line, so adding a guard means adding its breakage in the same commit. Twenty one cases were observed on 8 Aug 2026: twenty guards fired, and the untouched copy passed.

Two things that harness has already caught, both invisible by reading:

- **The stitcher pasted the wrong rows at the bottom of a tall page.** `verify-tiling.mjs` found it. The fix was not the first fix either: the second attempt was still one device pixel out, because the final scroll offset is clamped by the end of the document and routinely lands on a half CSS pixel.
- **`producer | grep -q needle` reports failure when it matches** under `set -o pipefail`, because grep exits at the first hit and the producer dies on the closed pipe. That made the harness declare a healthy baseline broken.

A guard you have never seen fire is not a guard: an overflow check that silently matches nothing prints "fits ok" for every card, and a click on a selector that does not exist looks exactly like a click that worked.
